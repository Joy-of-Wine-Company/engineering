How we test a compliance engine

A wrong answer from ordinary software is a bug. A wrong answer from a compliance engine can be a merchant's license. So the test suite is built around one uncomfortable requirement: it must be able to catch us — including the failure mode where the engine and its tests agree with each other and are both wrong.

The cardinal rule

A test fixture never takes its expected value from the engine under test.

Ground truth is external: state statutes, regulator publications, Department of Revenue rate tables, and independent commercial references — never our own output. This closes the classic laundering loop where a defective engine generates the fixtures that then certify the defective engine. Every expected verdict, cap, rate, and reason code in the fixtures library traces to a source we don't control. The Five Nines memo is the same principle applied to the data; this page is that principle applied to the code.

The layers

1

Coverage — does the engine know the rules?

Per-jurisdiction fixtures assert the shipping verdict (open, limited, prohibited), volume caps and their cumulative behavior across multiple orders, license and permit gating (expired, missing, wrong-state), and the 21+ age and adult-signature gate — decision and reason code, checked against actual law.

2

Adversarial — can the rules be defeated?

Separate from coverage, negative testing attacks the blocks themselves: malformed state codes, ZIP-to-state mismatches, spoofed destinations, override flags, and boundary probing around every cap. "It blocks the prohibited state" and "the prohibition cannot be routed around" are different claims; we test both.

3

Parity — same answer on every surface.

The same fixture must produce the same verdict through every path: the desktop app, each commerce-platform integration, and the live pre-ship API. Cross-surface parity is the core assertion — an integration that silently diverges from the engine is treated as a compliance defect, not a plumbing issue.

4

Data integrity — the numbers tie back.

Synced records land intact (field mapping, no drops, no duplicates — especially the fields the gate depends on), generated state and federal reports are checked for correct numbers rather than merely successful generation, and cross-system reconciliation confirms the same figure agrees everywhere it appears: tax computed vs. independent references, charges vs. recorded revenue, cases shipped vs. cases reported.

5

Boundaries — tenants, sessions, and actions.

Multi-tenant isolation (one winery can never read or affect another's data or decisions), multi-client consultant scoping (the right client's rules on every action, no leakage on switch), authentication hardening (second factor can't be bypassed or replayed, sessions expire, lockouts hold), and an access log that records every sensitive action with an attributable actor and timestamp.

6

Resilience — what happens when it's slow or down.

Latency SLAs under normal and burst load, circuit-breaker and degradation behavior, and the defining assertion: the gate fails closed — it never allows an order it could not fully evaluate. The full design for failure is its own page: fail-safe by design.

7

Evidence — every decision is findable later.

Audit-trail integrity testing asserts that every gate decision is written, retrievable, complete, and immutable. This layer exists because a live check once found a decision the audit endpoint couldn't return — the class of silent failure a regulator audit would surface at the worst possible moment, so now a test surfaces it first.

Testing the reference data itself

Code can be correct and the answer still wrong if the rule data underneath has gone stale. So the rule data is audited directly against external legal authority — prohibited-state lists, volume caps, and tax tables re-checked against current law, not against the engine. This hunt exists because it has caught real drift: stale reference entries found and corrected before they produced a wrong verdict in production. The climb log records that same discipline on the tax-rate side, including the audits that moved our numbers down.

How a run becomes a decision

Every failure is reproduced deterministically before it's filed — a minimal, version-pinned reproduction capturing the verdict, reason codes, and the rule-engine and data versions, so the fix targets the right rule instead of the symptom. Runs roll up into a single scorecard: pass rate, the compliance-risk metrics, a regression diff against the last green run, and an explicit GO / NO-GO ship verdict. Nothing ships on a NO-GO, and a "mostly green" run is a NO-GO with extra steps.
