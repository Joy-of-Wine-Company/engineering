Fail-safe by design

Compliance software lives inside a contradiction: it must never wrongly allow a shipment, and it must never break commerce. You cannot resolve that with uptime alone — every system eventually degrades. You resolve it by deciding, in advance and per question, which direction each failure is allowed to fall.

The asymmetry

Fails closed — into review

Legality

The gate never waves through an order it could not fully evaluate. When the engine is degraded, the answer is not "yes by default" — it's hold. And because a held order must never be a lost order, holding means the order proceeds into a flagged compliance-review queue, not into the void. Closed for compliance, open for commerce.

Fails open — to a safe floor

Tax

Rate resolution falls back, never forward: the address-level resolver falls back to the ZIP-level rate on any miss or timeout, and the ZIP level falls back to a conservative base that never over-collects a customer. A fallback can under-collect by a local increment — a known, bounded, correctable error — but it can never take money it shouldn't.

The principle underneath

When uncertain, err in the direction that cannot harm.

Never over-collect a customer's tax. Never silently under-enforce the law — uncertainty becomes a flagged hold, not a quiet yes. And never lose the evidence: every decision, including every fallback decision, lands in the tamper-evident audit trail, so a failure mode is always visible after the fact rather than discovered in a regulator's audit.

Receipts

  • The fallback floor is load-bearing, not theoretical. In the Five Nines data program, every ZIP we can't verify to ≥99% address-level correctness serves the conservative base on purpose — hundreds of ZIPs choose the safe floor over a plausible-but-unproven local rate.
  • Corrections prefer the harmless direction. Where independent evidence disagreed with our stored rate, downward corrections shipped on strong evidence while upward moves on thin samples were deferred — raising a rate on clustered samples is the risky direction, so it waits for proof.
  • Fail-open is proven, not assumed. The address-level resolver shipped dark behind a flag, with tests asserting fail-open on every miss — including an injected resolver exception — before it ever served a live answer, and a per-merchant gate so enforcement expands only by explicit opt-in.
  • Degradation is a tested surface. Latency SLAs, burst behavior, and circuit breakers are part of the standing test suite — "what does the gate do when it is slow or down" is a first-class test case, not an incident retrospective.
